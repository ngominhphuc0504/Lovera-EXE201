CHAPTER 1
INTRODUCTION
1.1. Background
In contemporary computer networking, Internet Protocol (IP) routing serves as the fundamental mechanism governing packet forwarding across autonomous systems, enterprise intranets, and campus infrastructures. Within this operational ecosystem, static routing and default routing constitute critical building blocks. Unlike dynamic routing protocols such as Open Shortest Path First (OSPF) or Border Gateway Protocol (BGP)—which introduce continuous control-plane signaling, protocol overhead, and computational demands—static routing provides deterministic path selection, predictable traffic engineering, zero bandwidth consumption for route updates, and minimal processing overhead. Consequently, static and default routes are extensively deployed at network peripheries, stub networks, demarcation gateways, and point-to-point interconnects to establish egress connectivity and enforce security policies.
Despite these operational advantages, static and default routing schemes possess an intrinsic structural vulnerability: they lack autonomic self-healing, dynamic path renegotiation, and real-time state adaptation. Because forwarding entries are manually provisioned by human operators, they are highly susceptible to configuration oversights and typographical mistakes. Common misconfigurations—such as specifying an unreachable or incorrect next-hop IP address, configuring an erroneous subnet mask or prefix length, conflicting route metrics, or completely omitting a default route (0.0.0.0/0)—inevitably disrupt end-to-end connectivity, leading to catastrophic routing blackholes, forwarding loops, or silent packet drops [2], [6]. As enterprise networks scale horizontally with multi-tiered architectures and redundant paths, the interdependencies among routing entries across multiple hops become increasingly complex, exponentially multiplying the risk of human-induced configuration failures.
Traditionally, network troubleshooting has remained a predominantly manual and reactive process. When end-to-end connectivity fails, network administrators rely on standard Command-Line Interface (CLI) diagnostic utilities, specifically Internet Control Message Protocol (ICMP) echo probes (ping) and hop-by-hop route tracing (traceroute), in conjunction with inspecting local routing tables (show ip route) [1], [3]. However, interpreting raw textual diagnostic outputs and manually correlating routing tables across dozens of intermediary routers is an exhausting, time-consuming, and error-prone endeavor [1], [4]. An anomaly observed at a destination host (e.g., packet timeout or unreachable destination) frequently stems from a misconfiguration residing multiple hops upstream, masking the true root cause and inflating Mean Time to Repair (MTTR).
In response to these challenges, the integration of Artificial Intelligence (AI), Machine Learning (ML), and Explainable AI (XAI) into network operations has emerged as a transformative paradigm. By combining control-plane routing table states with active data-plane diagnostic telemetry, intelligent systems can automate telemetry parsing, synthesize end-to-end forwarding behavior, localize the root cause of routing misconfigurations, and formulate actionable, verifiable repair recommendations [4], [5], [7], [9]. This research focuses on conceptualizing and developing an AI-assisted troubleshooting framework tailored specifically to diagnosing static and default route misconfigurations in computer networks.




1.2. Problem Statement
Although the necessity of automated network diagnostics is widely recognized, diagnosing static and default routing misconfigurations through AI introduces three critical technical hurdles, which directly correspond to the core research questions of this study:
Challenge 1: Data Heterogeneity, Unstructured CLI Syntaxes, and the Semantic Gap (RQ1)
Network diagnostic data is fundamentally heterogeneous and multi-modal. Routing tables represent static, localized control-plane snapshots stored in memory, whereas ping and traceroute represent dynamic, end-to-end data-plane telemetry [1], [3]. Furthermore, router diagnostic outputs are emitted as vendor-specific, unstructured textual CLI streams (e.g., Cisco IOS, VyOS, Juniper Junos), which lack standard tabular schemas. Existing diagnostic frameworks typically focus either on static configuration verification [2] or on Internet-scale traceroute delay anomalies [3], failing to provide an automated, unified preprocessing pipeline that normalizes CLI strings, extracts structured topological features, and detects deviations between expected forwarding paths and observed packet trajectories. Transforming raw, unstructured routing tables and probe outputs into a high-fidelity feature representation suitable for AI ingestion remains an unresolved challenge.

Challenge 2: Combinatorial Fault Localization in Scalable Topologies (RQ2)
In multi-hop topologies, localizing the precise origin of a routing fault is a non-trivial combinatorial problem. A single misplaced static route or erroneous default gateway on an intermediate router can propagate forwarding anomalies across multiple downstream devices, producing symptoms such as blackholes or routing loops that manifest far from the offending device [1], [5]. Conventional rule-based scripts and manual inspections degrade rapidly as network scale and link density expand. While supervised machine learning models (e.g., Decision Trees, Random Forests, XGBoost) demonstrate high accuracy on structured tabular datasets [4], they process feature vectors independently and remain inherently oblivious to graph topology. Conversely, Graph Neural Networks (GNNs) natively capture topological dependencies and router interconnections [5]. However, there is an absence of systematic empirical benchmarks that determine which AI architecture achieves optimal localization accuracy and scalability specifically for static and default route misconfigurations.

Challenge 3: The Black-Box Trust Deficit and Lack of Verifiable Remediation (RQ3)
Modern machine learning architectures operate predominantly as opaque black boxes, delivering predictions without interpretable reasoning [7], [8]. In mission-critical enterprise environments, network engineers cannot responsibly execute configuration modifications based solely on an unexplained model output flagging a router as faulty. Without transparent rationales elucidating why an entry was deemed erroneous, operators experience an acute trust deficit. Moreover, while recent explorations leverage generative Large Language Models (LLMs) to formulate configuration repairs, unconstrained LLMs are prone to generating hallucinated CLI commands or syntactically invalid fixes that can exacerbate network instability [6], [9]. Consequently, bridging post-hoc feature attribution (e.g., SHAP [7], GNNExplainer [8]) with constraint-validated, human-in-the-loop CLI repair recommendations [9] is imperative to ensure both operational trust and network safety.




1.3. Research Objectives
The overarching goal of this study is to conceptualize, implement, and empirically evaluate an end-to-end AI-assisted troubleshooting framework that ingests routing tables and ping/traceroute diagnostic telemetry, accurately detects and localizes static/default routing misconfigurations, and delivers explainable, verifiable remediation recommendations. To accomplish this overarching goal, three specific research objectives are formulated in direct alignment with the research questions:
Objective 1 (Addressing RQ1 - Data Normalization and Anomaly Feature Engineering):
To develop a standardized data preprocessing and feature extraction pipeline utilizing template-based parsing (TextFSM and regular expressions) to transform heterogeneous, raw CLI outputs from routing tables, ping statistics, and traceroute hop paths into normalized JSON structures and engineered feature vectors. This pipeline will compute routing consistency metrics, next-hop reachability flags, prefix overlaps, and forwarding-path deviation scores, thereby enabling the reliable detection of routing anomalies [1]–[3].

Objective 2 (Addressing RQ2 - AI Architecture Benchmark and Fault Localization):
To design, train, and comparatively evaluate multiple AI architectures—contrasting high-performance tabular machine learning models (Random Forest, XGBoost [4]) with a topology-aware Graph Neural Network (GNN / GraphSAGE [5])—to accurately classify misconfiguration categories (e.g., invalid next-hop, missing static route, missing default route, wrong destination prefix/mask) and pinpoint the exact faulty router and routing table entry across varied network topologies and scales.

Objective 3 (Addressing RQ3 - Explainable Diagnosis and Validated Configuration Recommendations):
To formulate an explainable AI and remediation framework integrating feature and subgraph attribution mechanisms (SHAP [7], GNNExplainer [8]) with an LLM-assisted configuration repair module [9]. The system will generate transparent diagnostic justifications correlating model decisions with underlying routing rules, while subjecting proposed router CLI remediation scripts to formal network verification constraints [6], [9] under a human-in-the-loop paradigm.





1.4. Significance of the Study
The findings and artifacts developed in this research deliver both significant practical utility for network operations and notable academic contributions to the field of intelligent computer network management:
* Practical Significance:
In enterprise and campus network environments, static and default routing misconfigurations represent a persistent source of unscheduled downtime. By automating the ingestion and correlation of routing tables and active diagnostic telemetry, the proposed framework substantially reduces Mean Time to Detect (MTTD) and Mean Time to Repair (MTTR). Furthermore, by translating complex topological anomalies into plain-language diagnostic rationales and verified CLI repair commands, the system bridges the technical expertise gap, empowering junior network administrators to resolve intricate multi-hop routing failures swiftly and safely.

* Academic Significance:
From an academic perspective, this research bridges the conventional divide between static configuration verification [2], [6] and active data-plane telemetry [1], [3] within an integrated AI-driven framework. It contributes a rigorous, empirical benchmark comparing the diagnostic efficacy of tabular machine learning against graph representation learning on routing configuration anomalies [4], [5]. Furthermore, it demonstrates how post-hoc XAI techniques [7], [8] can be practically coupled with constraint-checked generative configuration repair [9], establishing a robust blueprint for safe, explainable AI in computer network operations.




1.5. Scope and Limitations
To maintain scientific rigor and operational feasibility within the scope of this course project, the boundaries and constraints of the study are defined as follows:
Target Routing Protocols: The investigation focuses strictly on IPv4 static routing and default routing (0.0.0.0/0). This encompasses direct next-hop IP routing, exit-interface routing, recursive static routes, and floating static routes characterized by customized administrative distances.
Network Environments and Testbeds: Experiments are conducted across simulated and emulated enterprise network topologies designed in network simulation platforms (e.g., Cisco Packet Tracer, GNS3, and Mininet) utilizing standard router operating systems (Cisco IOS and VyOS/Linux FRRouting).
Diagnostic Input Modalities: System inputs are limited to three ubiquitous diagnostic modalities: router routing tables (obtained via show ip route), ICMP echo ping outputs (evaluating reachability, packet loss, and round-trip time), and traceroute outputs (capturing sequential hop IP addresses and path progress).
Fault Scenarios Supported: The research models four primary classes of static/default route misconfigurations: (1) missing static route, (2) missing default route, (3) invalid or unreachable next-hop IP address, and (4) erroneous destination prefix or subnet mask, resulting in symptoms such as routing loops, blackholes, and asymmetric unreachability.
Known Exclusions and Limitations: Dynamic routing protocols (e.g., OSPF, EIGRP, BGP) and IPv6 addressing are excluded from the primary scope of this study and designated for future extensions. Diagnostic telemetry is gathered via periodic on-demand CLI polling and active probing rather than continuous high-frequency streaming telemetry (such as gNMI or sFlow). Finally, the system operates under a human-in-the-loop advisory model: generated CLI remediation scripts are verified against configuration constraints and presented to network engineers for explicit authorization, rather than being autonomously executed on production infrastructure [9].

Chapter 6 (Conclusion and Future Work): Summarizes the principal achievements and verified contributions of the study, reflects on research limitations, and proposes promising directions for future investigations, including dynamic routing extensions and autonomous remediation.

CHAPTER 2
LITERATURE REVIEW
2.1. Review of Previous Studies
Diagnosing and troubleshooting connectivity anomalies in IP networks requires synthesizing control-plane routing state data with active data-plane diagnostic telemetry. As articulated in Section 1.2, identifying and remediating static and default route misconfigurations poses three fundamental technical hurdles: data heterogeneity in unstructured CLI streams, combinatorial fault localization across multi-hop topologies, and the lack of transparent, verifiable remediation. To establish the theoretical grounding and delineate the technological boundaries of this research, existing literature is surveyed across three core investigative domains: (1) Active probing, routing data normalization, and static verification (addressing RQ1); (2) Machine learning and graph neural network paradigms for network fault localization (addressing RQ2); and (3) Explainable Artificial Intelligence (XAI) coupled with safe, automated configuration remediation (addressing RQ3). 
2.1.1. Active Probing, Routing Data Normalization, and Static Verification (Addressing RQ1)
The earliest systematic network diagnostic methodologies relied heavily on active probing to observe packet forwarding behaviors in transit. Fontugne et al. [3] analyzed distributed, large-scale traceroute telemetry to detect data-plane forwarding anomalies and latency degradation. By modeling packet transitions as directed hop-by-hop sequences, their work demonstrated that active traceroute measurements are essential for pinpointing intermediate forwarding breaks, silent packet discards, and sub-optimal next-hop deviations. Similarly, Dhamdhere et al. introduced NetDiagnoser [1], a pioneering framework that formalizes network failure localization by correlating end-to-end active probe paths with underlying routing data. Utilizing Boolean tomography and satisfiability modeling, NetDiagnoser infers the minimal candidate set of link outages or misconfigured route export filters capable of explaining observed path unreachabilities.
In parallel with empirical telemetry analysis, formal static verification has emerged to preemptively identify routing vulnerabilities directly from configuration code. Fogel et al. developed Batfish [2], an extensible static analysis platform that parses multi-vendor network configurations into vendor-agnostic abstract syntax trees (ASTs). Batfish simulates control-plane message propagation to construct predicted Routing Information Bases (RIBs) and Forwarding Information Bases (FIBs), verifying end-to-end reachability invariants and identifying forwarding loops. Extending static checking to arbitrary packet headers, Beckett et al. presented Minesweeper [6], which translates routing configurations into Satisfiability Modulo Theories (SMT) formulas. Minesweeper provides provable mathematical guarantees regarding network reachability, routing blackholes, and path compliance across all possible environment states.
Critique and Limitations: Despite their mathematical rigor, existing active probing and formal verification systems exhibit critical operational shortcomings when applied to interactive static route troubleshooting. First, formal verifiers such as Batfish [2] and Minesweeper [6] operate exclusively on complete, global configuration archives; they lack the ability to ingest partial, ad-hoc CLI diagnostic snapshots (show ip route) produced during emergency incident response. Second, pure active probing frameworks [1], [3] observe symptoms on the data plane but cannot inspect control-plane routing logic to determine why a router dropped a packet (e.g., distinguishing between a physical interface failure, an erroneous subnet mask, or a missing reverse path). Furthermore, prior works assume pre-structured data schemas, failing to provide an automated preprocessing pipeline that parses raw, semi-structured CLI texts into normalized topological graphs and prefix-matching feature structures suitable for intelligent anomaly detection.


2.1.2. Machine Learning and Graph Architectures for Network Fault Localization (Addressing RQ2)
To mitigate the computational rigidity and exhaustive configuration dependencies of formal SMT solvers, researchers have increasingly deployed data-driven machine learning (ML) architectures to automate network fault identification.
Mohammed et al. [4] investigated supervised machine learning models for network status classification and fault localization. By collecting telemetry metrics spanning latency, jitter, packet loss ratios, and interface statistics, their study trained tree-based classifiers—such as Decision Trees and Random Forests—to categorize operational network anomalies and localize faulty link segments. These tabular learning algorithms achieve high classification throughput and robust performance on fixed-dimensional telemetry datasets, effectively classifying known failure patterns under stationary traffic distributions.
However, computer networks are inherently non-Euclidean, relational graphs where nodes represent routers and edges denote communication links. Standard tabular machine learning models treat input features independently, remaining oblivious to network topology and path interdependencies. When routing faults propagate across multi-hop paths, an anomaly on an upstream device manifests as failure symptoms on distant downstream nodes, confusing flat vector models. To capture structural dependencies, Sun et al. [5] formulated Hybrid-GNN, an edge-enhanced Graph Neural Network (GNN) tailored for concurrent node and link fault diagnosis in complex interconnection networks under the HPMC* model. By recursively aggregating feature representations from local topological neighborhoods, GNN architectures capture spatial message-passing dynamics and model topological routing dependencies far more effectively than flat classifiers.
Critique and Limitations: While tabular ensemble models (Random Forest, XGBoost) offer rapid training and inferential simplicity [4], their topological blindness limits their diagnostic accuracy when evaluated on arbitrary or scaled enterprise topologies. Conversely, while GNNs natively encode topological relationships [5], existing network-oriented GNN frameworks are predominantly trained on abstract synthetic fault models rather than realistic control-plane routing tables and ICMP diagnostic telemetry. Currently, there is an absence of systematic, comparative empirical benchmarks evaluating whether topology-aware GNN architectures (e.g., GraphSAGE) genuinely outperform optimized tabular ensemble models in localizing specific static and default routing defects (such as invalid next-hops, cyclic loops, and recursive routing blackholes).










2.1.3. Explainable AI and Safe Automated Configuration Repair (Addressing RQ3)
Although deep neural networks and GNNs achieve superior predictive performance, their practical adoption in mission-critical network environments is severely hindered by their opaque, "black-box" decision-making nature. In operational enterprise environments, network engineers are reluctant to modify routing configurations based purely on uninterpretable model predictions.
To establish operational trust, post-hoc Explainable AI (XAI) frameworks have been introduced to interpret complex model decisions. Lundberg and Lee [7] formulated SHAP (SHapley Additive exPlanations), a game-theoretic approach that assigns each input feature an optimal Shapley marginal contribution value for a specific prediction. In network fault diagnosis, SHAP enables administrators to discern which specific feature (e.g., high prefix overlap, next-hop unreachable flag, or hop-count divergence) triggered an anomaly classification. To address graph-structured data specifically, Ying et al. developed GNNExplainer [8]. GNNExplainer provides compact, subgraph-level interpretability by isolating the crucial subset of inter-router edges and node features that predominantly govern a GNN's diagnostic inference, thereby highlighting the exact forwarding path segment responsible for a routing failure.
Beyond fault localization, the ultimate frontier of network troubleshooting is automated configuration remediation. Recent advancements in generative Large Language Models (LLMs) demonstrate remarkable potential in synthesizing CLI configuration commands from natural-language incident prompts. However, unconstrained LLM agents frequently suffer from hallucinations, generating invalid command syntaxes or proposing routing modifications that introduce catastrophic circular loops. To address this risk, Asadli et al. [9] proposed an agentic configuration repair framework for computer networks that integrates LLM reasoning with formal network verification tools. By subjecting candidate configuration patches to rigorous constraint validation before deployment, their work illustrates the feasibility of safe, automated remediation.
Critique and Limitations: While feature-attribution techniques (SHAP [7]) and subgraph explanation methods (GNNExplainer [8]) effectively identify important features and topologies, they provide diagnostic evidence in abstract mathematical or graphical formats rather than actionable networking recommendations. A network administrator cannot directly translate a Shapley value or a highlighted subgraph into a concrete Cisco IOS configuration command. Furthermore, while agentic LLM repair systems [9] show promise, they generally require access to full network emulation containers for validation. A critical research gap remains in bridging post-hoc XAI attributions with constraint-validated, human-in-the-loop CLI repair generation tailored specifically for ad-hoc static and default routing workflows.

A comprehensive analysis of Table 2.1 reveals two overarching polarities in contemporary network troubleshooting:
   1. The Visibility-Computation Dilemma: Existing diagnostic systems either demand exhaustive, global configuration visibility (e.g., Batfish [2], Minesweeper [6], Asadli et al.    2. The Black-Box Trust Dilemma: Advanced data-driven classifiers (Mohammed et al. [4], Sun et al. [5]) achieve impressive anomaly detection rates but function as opaque black boxes, while standalone XAI mechanisms (SHAP [7], GNNExplainer [8]) output mathematical attributions that lack actionable networking semantics and syntax-compliant remediation commands.
Consequently, there is a distinct void in the literature for an integrated, lightweight diagnostic framework that:
   * Ingests semi-structured, heterogeneous CLI routing tables and ICMP diagnostic telemetry, converting them into standardized graph structures and prefix-matching features (Challenge 1 / RQ1).
   * Systematically evaluates whether topology-aware GNN architectures provide superior localization precision over optimized tabular ensemble classifiers for static and default routing faults (Challenge 2 / RQ2).
   * Unifies post-hoc feature attribution with constraint-checked LLM command generation under a human-in-the-loop paradigm, delivering transparent, verifiable, and deployable remediation scripts (Challenge 3 / RQ3).


2.3. Contribution of Research
To bridge the delineated research gaps and accomplish the specific research objectives defined in Section 1.3, this thesis develops an end-to-end, AI-assisted troubleshooting framework for static and default routing misconfigurations. The explicit contributions of this work are threefold:
   1. Standardized CLI Ingestion and Forwarding-Graph Feature Engineering Pipeline (Fulfilling Objective 1):
The development of an automated parsing engine utilizing TextFSM templates and regular expressions to ingest raw, multi-vendor CLI outputs (Cisco IOS and VyOS) from show ip route, ping, and traceroute. The pipeline transforms unstructured text into normalized JSON schemas and constructs a unified forwarding-path graph. From this representation, the system extracts high-fidelity diagnostic feature vectors—including Longest Prefix Match (LPM) consistency, next-hop reachability flags, administrative distance disparities, and traceroute path deviation scores—enabling the automated detection of routing blackholes, loops, and asymmetric drops.

   2. Empirical Architectural Benchmark for Fault Localization (Fulfilling Objective 2):
The design, implementation, and rigorous benchmarking of diverse AI localization models across multiple network topologies (linear topologies, hub-and-spoke enterprise edges, and cyclic meshes) and scales. By contrasting high-performing tabular ensemble models (Random Forest, XGBoost) against a topology-aware Graph Neural Network (GNN utilizing GraphSAGE message passing), this research provides empirical evidence regarding the trade-offs between inferential speed, computational overhead, and topological generalization when localizing missing static routes, omitted default gateways, and erroneous subnet masks.

   3. Explainable Diagnosis with Constraint-Validated CLI Remediation (Fulfilling Objective 3):
The integration of a dual-layered explainable remediation framework combining post-hoc feature and subgraph attribution (SHAP and GNNExplainer) with an LLM-assisted configuration repair module. The system translates abstract mathematical attributions into intuitive, plain-language diagnostic explanations that articulate the exact root cause of the routing failure. Furthermore, the proposed remediation module synthesizes syntax-compliant Cisco IOS CLI commands (e.g., ip route [destination-prefix] [subnet-mask] [next-hop-IP]) and validates them against domain-specific routing constraints and basic reachability rules [6], [9], ensuring safe, human-in-the-loop operational deployment.

CHAPTER 3
METHODOLOGY
3.1. Research Design
This research adopts an experimental and quantitative approach to investigate an Artificial Intelligence (AI)-assisted troubleshooting system for static and default routing misconfigurations. The proposed system integrates routing table analysis, ping and traceroute measurements, machine learning, Graph Neural Networks (GNN), and Explainable Artificial Intelligence (XAI) to identify routing anomalies, locate misconfigured routers, and generate interpretable configuration repair recommendations.
Traditional network troubleshooting relies on manual examination of routing information and network diagnostic results. Dhamdhere et al. [1] demonstrated that combining routing information with end-to-end network measurements can support fault localization. Similarly, Fogel et al. [2] introduced a configuration analysis framework capable of deriving forwarding behavior from network configurations. These studies provide a foundation for the proposed integration of routing data and diagnostic measurements.
The methodology is designed to address the three research questions:
      * RQ1: How can AI normalize and extract features from routing tables combined with ping/traceroute results to detect routing anomalies?
      * RQ2: Which AI model is most effective in accurately localizing static/default route configuration errors across network topologies of varying sizes?
      * RQ3: How can explainable AI help network engineers understand and evaluate routing fault diagnoses and configuration repair recommendations?
The research design consists of five stages: network simulation, data collection, data preprocessing and feature extraction, AI-based fault localization, and explainable configuration recommendations.
Network Simulation and Experimental Environment
A controlled networking environment will be developed using GNS3 or EVE-NG, subject to the selected platform's support for the required routing commands and configuration features. The environment will include routers, network links, and end devices configured with IPv4 static routes and default routes.
The study will investigate several topology structures, including linear, star, ring, and mesh networks. Different topology sizes will be considered to evaluate model performance as network complexity increases.
Each topology will initially be configured to provide valid connectivity between selected source and destination networks. Controlled routing configuration errors will then be introduced into the environment.
The investigated errors will include incorrect next-hop addresses, missing static routes, missing default routes, inappropriate destination prefixes, and forwarding loops resulting from inconsistent route configurations.
Static routing behavior will be evaluated according to IPv4 routing principles, including destination prefix matching and next-hop selection.
Proposed System Architecture
The proposed system will consist of five functional modules:
      1. Data Collection Module: Collects routing tables, ping results, traceroute outputs, and network topology information.
      2. Data Preprocessing Module: Converts raw network diagnostic outputs into standardized JSON records.
      3. Anomaly Detection Module: Extracts routing and forwarding features to identify abnormal behavior.
      4. AI-Based Fault Localization Module: Uses machine learning and graph-based models to classify routing errors and identify suspected faulty routers.
      5. Explainable AI and Recommendation Module: Generates explanations and proposes configuration corrections based on diagnostic evidence.
The overall workflow will follow the sequence:
Network Simulation → Data Collection → Data Preprocessing → Feature Extraction → AI Fault Localization → Explainable AI → Configuration Recommendation → Validation.
This architecture is intended to support an integrated troubleshooting process in which AI predictions can be interpreted and checked against network evidence.
3.2. Data Collection Methods
The study will collect data from controlled network experiments. The main data sources include routing table outputs, ping measurements, traceroute results, and network topology information.
Data collection will be performed under both normal routing conditions and intentionally introduced misconfiguration scenarios.
Routing Table Data Collection
Routing tables describe how routers select forwarding paths toward destination networks. For Cisco IOS-based environments, commands such as show ip route and show running-config can provide routing information and configuration entries.
The collected attributes will include router identifiers, destination networks, prefix lengths, next-hop addresses, outgoing interfaces, and route types.
These routing attributes will be used to identify inconsistencies between configured routes and expected forwarding paths.
Ping Data Collection
Ping measurements will be collected to evaluate reachability between selected source and destination devices.
The recorded information will include source and destination addresses, packet transmission results, packet loss, and round-trip time measurements where available.
Ping results will be treated as connectivity observations rather than direct evidence of a particular routing configuration error.
Traceroute Data Collection
Traceroute results will be collected to observe responding network hops along the path toward a destination.
The collected fields will include hop numbers, responding IP addresses, round-trip times, and timeout indicators.
Fontugne et al. [3] demonstrated that large-scale traceroute measurements can support the detection of network delay and forwarding anomalies.
In the proposed study, traceroute observations will be compared with expected forwarding behavior derived from routing information and topology data.
Missing responses or repeated hop addresses will be treated as potential anomaly indicators requiring additional verification.
Fault Scenario Generation
Controlled configuration errors will be introduced into selected routers to generate labeled experimental cases.
The proposed scenarios include:
      * Missing static route.
      * Missing default route.
      * Incorrect next-hop address.
      * Incorrect destination prefix.
      * Forwarding loop caused by inconsistent route configurations.
      * Normal routing operation.
Each experimental scenario will be associated with a configuration record identifying the introduced error, the responsible router, and the affected routing entry where applicable.
A single-fault assumption will be used for the initial fault localization experiments to maintain unambiguous ground-truth labels. Multiple simultaneous faults may be considered in an extended evaluation.
Data Normalization and Storage
Raw CLI outputs will be processed using TextFSM and regular expressions.
TextFSM provides a template-based approach for extracting structured information from network device command outputs.
The extracted information will be normalized into JSON records containing routing attributes, connectivity observations, traceroute hop sequences, and topology identifiers.
The preprocessing process will include IP address normalization, duplicate checking, missing-field identification, and validation of extracted values.
The resulting records will be stored as structured experimental data for subsequent feature extraction and model training.
Ground-Truth Labeling
Ground-truth labels will be generated from the controlled configuration changes introduced during each experiment.
Each sample will contain the observed diagnostic features together with its fault category, responsible router, and affected routing entry where applicable.
Labels will not be inferred solely from ping or traceroute results because similar network symptoms may originate from different causes.
Samples will be validated by comparing the injected configuration error with the observed network behavior and the original functional configuration.
3.3. Sampling Data Analysis Techniques
This section describes the proposed sampling strategy, feature engineering process, machine learning models, explainability methods, and evaluation metrics.
Sampling Strategy
The dataset will be generated from combinations of network topologies, routing configurations, source-destination pairs, and controlled fault scenarios.
Both normal and abnormal conditions will be included to support anomaly detection and fault classification.
The sampling process will aim to provide adequate representation of each fault category. The final number of scenarios and samples will be determined according to the implemented experimental environment.
The dataset will be divided into training, validation, and test subsets.
To reduce data leakage, observations originating from the same configuration instance will remain within the same dataset partition.
An additional topology-level evaluation will be considered to examine model generalization to network structures not encountered during training.
Data Preprocessing and Feature Extraction
The normalized dataset will be transformed into diagnostic features describing routing behavior and network connectivity.
The proposed feature categories include:
Routing Features
      * Route availability for a selected destination.
      * Destination prefix length.
      * Next-hop consistency.
      * Outgoing interface consistency.
      * Default route availability.
      * Selected forwarding route.
Ping Features
      * Destination reachability.
      * Packet loss ratio.
      * Average round-trip time.
      * Connectivity status across selected source-destination pairs.
Traceroute Features
      * Number of responding hops.
      * Number of timeout observations.
      * Differences between expected and observed paths.
      * Repeated responding router addresses.
      * Last responding hop.
Topology Features
      * Router adjacency relationships.
      * Router degree.
      * Expected forwarding path.
      * Relative position of the suspected faulty router.
      * Path deviation characteristics.
The forwarding graph will be constructed from topology and routing information.
Network devices will be represented as nodes, while communication links and relevant forwarding relationships will be represented as edges.
The graph-based representation is intended to support analysis of routing dependencies between interconnected routers.
Machine Learning Models
Three machine learning approaches will be investigated.
Random Forest
Random Forest will be used as a baseline model for fault classification and localization.
The model combines multiple decision trees to generate predictions from structured diagnostic features.
Its performance will provide a reference for evaluating more complex learning approaches.
XGBoost
XGBoost will be evaluated as a gradient-boosted tree-based model.
In network troubleshooting, Mohammed et al. [4] demonstrated the potential of tree-based models, including Extreme Gradient Boosting, for network status detection and fault localization.
The proposed study will investigate whether XGBoost can accurately classify static/default route misconfigurations and identify affected routers using the extracted diagnostic features.
Graph Neural Network
A Graph Neural Network will be investigated to incorporate network topology relationships into the fault localization process.
Sun et al. [5] demonstrated the application of a Graph Neural Network-based architecture to node and edge fault diagnosis in interconnection networks.
The proposed study will investigate whether graph-based learning can improve static/default route fault localization compared with traditional feature-based models.
Routers will be represented as nodes with routing and diagnostic features, while edges will represent relevant network relationships.
A node-level prediction approach will be considered to estimate which router is associated with a configuration error.
The final choice of models will depend on dataset characteristics, computational requirements, and experimental feasibility.
Model Training and Performance Evaluation
The models will be trained using labeled fault scenarios.
Hyperparameters will be selected using training and validation data, while the test dataset will be reserved for final performance evaluation.
The primary classification metrics will include Accuracy, Precision, Recall, and Macro-F1 Score.
Accuracy measures the proportion of correctly classified samples.
Precision measures the proportion of predicted instances belonging to a category that are correctly classified.
Recall measures the proportion of actual instances of a category that are successfully identified.
The F1-score provides a combined measure of precision and recall.
Macro-F1 will be used to evaluate multiclass performance without allowing large classes to dominate the final score.
Fault localization will be evaluated using:
      * Router-Level Localization Accuracy: The proportion of applicable faulty test cases in which the responsible router is correctly identified.
      * Route-Entry Localization Accuracy: The proportion of applicable faulty test cases in which the erroneous route entry is correctly identified.
      * Top-k Localization Accuracy: The proportion of cases in which the actual faulty router appears among the model's top-k predictions, when ranking output is available.
      * Inference Time: The time required to generate a diagnostic prediction.
Classification performance and fault localization performance will be reported separately because correctly identifying a fault category does not necessarily imply correctly locating the responsible router.
Results will be compared across different fault categories and network topology sizes.
Explainable AI Methods
The proposed study will investigate SHAP and GNNExplainer for interpreting AI-generated diagnostic predictions.
SHAP
SHAP, proposed by Lundberg and Lee [7], provides a method for attributing model predictions to input features.
SHAP will be considered for explaining predictions generated by Random Forest and XGBoost.
The analysis will investigate the importance of features such as route availability, next-hop consistency, and observed forwarding-path deviations.
GNNExplainer
GNNExplainer, proposed by Ying et al. [8], identifies influential subgraph structures and input features associated with Graph Neural Network predictions.
The method will be considered for explaining topology-aware fault localization results.
Its explanations may identify routers, neighboring connections, or diagnostic attributes that influenced a model's prediction.
The explanation outputs will be compared with the known faulty configurations to examine their relevance to the actual network problem.
Explanation methods will not be treated as independent proof of the predicted root cause.
LLM-Based Configuration Recommendations
The proposed system will investigate the use of a Large Language Model to generate diagnostic explanations and router-specific configuration recommendations.
The LLM will receive structured diagnostic evidence, including the predicted fault category, suspected router, relevant routing entries, and available XAI results.
The generated report will describe the suspected problem, explain the supporting observations, and suggest possible corrective configuration changes.
Asadli et al. [9] investigated LLM-based network configuration repair supported by verification and context retrieval mechanisms.
Building on this approach, the proposed system will validate candidate configuration recommendations before presenting them to network engineers.
Validation will examine whether the recommendation targets the intended router, uses the correct command syntax, modifies the relevant routing entry, and restores required forwarding behavior in the controlled environment.
The system will also examine whether previously valid network connectivity is preserved.
Configuration recommendations will be presented for review rather than automatically deployed to operational network devices.
Evaluation of the Research Questions
The experimental evaluation will be organized around the three research questions.
RQ1 Evaluation
The data preprocessing pipeline will be evaluated using parsing correctness, completeness of extracted fields, and anomaly detection performance.
RQ2 Evaluation
Random Forest, XGBoost, and the implemented graph-based model will be compared using fault classification performance, router-level localization accuracy, route-entry localization accuracy, and inference time.
RQ3 Evaluation
The explanation mechanisms will be evaluated for consistency with known routing faults. Generated configuration recommendations will be assessed using syntax validity, technical correctness, and verified repair success under controlled conditions.
The experimental results will be presented in Chapter 4.
3.4. Limitations of the Methodology
The proposed methodology has several limitations that may affect the interpretation and generalization of the experimental findings.
Controlled Experimental Environment
The research will primarily use simulated or emulated network topologies.
Although controlled experiments enable reproducible fault injection and data collection, they may not fully represent the variability of real-world production networks.
Dataset Representativeness
The dataset will consist of predefined fault scenarios generated under controlled conditions.
Models trained on these scenarios may not generalize to unfamiliar configurations, device platforms, or network environments.
Diagnostic Data Limitations
Ping and traceroute measurements may provide incomplete information because of ICMP filtering, asymmetric routing, load balancing, or missing router responses.
Consequently, incomplete measurements may produce ambiguous diagnostic features.
Fault Complexity
The initial experimental design will focus on isolated static/default route configuration errors.
Networks containing multiple simultaneous faults, dynamic routing interactions, or policy-based forwarding may require additional diagnostic methods.
Model Scalability
The performance and computational requirements of the evaluated AI models may vary with network size and topology complexity.
Therefore, the findings will only support scalability conclusions within the topology sizes actually evaluated.
Explainability Constraints
SHAP and GNNExplainer describe how input features or graph structures influence model predictions [7], [8].
They do not independently establish the true cause of a routing configuration failure.
Recommendation Reliability
LLM-generated configuration recommendations may contain incorrect assumptions, invalid commands, or incomplete corrective actions.
Independent validation and engineer review are therefore necessary before applying recommended changes.
Threats to Validity
Potential threats include class imbalance, data leakage, incomplete ground-truth labels, and differences in model tuning.
To reduce these risks, the study will use controlled fault injection, document experimental configurations, maintain appropriate dataset separation, and compare models under consistent evaluation conditions.
These limitations will be considered when interpreting the experimental results and determining the practical applicability of the proposed troubleshooting framework.

CHAPTER 4
EXPERIMENTAL AND RESULTS
4.1. Introduction
Network troubleshooting is an essential process for maintaining connectivity and ensuring the reliable operation of computer networks. In networks that use static routing and default routing, configuration errors such as missing routes, incorrect next-hop addresses, and misconfigured default routes can cause communication failures between network devices. Identifying these problems often requires administrators to examine routing tables and analyze diagnostic information obtained from tools such as Ping and Traceroute.
Previous studies have demonstrated the importance of combining network measurements and routing information to identify connectivity problems. Dhamdhere et al. [1] proposed NetDiagnoser, a troubleshooting approach that uses end-to-end probes and routing data to identify network failures. Similarly, Fogel et al. [2] introduced a network configuration analysis method capable of detecting configuration errors and examining their effects on packet forwarding.
Artificial intelligence and machine learning have also been investigated as approaches to network fault detection and diagnosis. Mohammed et al. [4] proposed a machine learning-based method for detecting network states and localizing faults. More recently, Asadli et al. [9] investigated AI-based network configuration repair, highlighting both the potential benefits of intelligent troubleshooting and the importance of validating proposed configuration changes.
Based on these research directions, this chapter presents the experimental framework for evaluating the proposed AI-based troubleshooting system for static and default routing. The experiments are designed around simulated network topologies containing normal routing configurations and deliberately introduced routing errors. Routing tables, Ping results, and Traceroute outputs serve as the primary diagnostic inputs for the AI-based analysis.
The evaluation focuses on determining whether the proposed system can identify routing problems, explain their possible causes, and recommend appropriate corrective actions. The experimental results will be analyzed to assess diagnostic accuracy, identify limitations, and examine the effectiveness of the proposed troubleshooting approach. The following sections describe the collected data, analysis of results, interpretation of findings, comparison with previous studies, and implications of the experimental evaluation.

4.4. Interpretation of Results
The experimental results provide insights into the effectiveness and limitations of Qwen3:4b in diagnosing static and default routing failures. The five test scenarios demonstrate how routing configuration errors affect network connectivity and how routing tables, Ping, and Traceroute results can support AI-assisted troubleshooting.
Interpretation of Network Connectivity Results
Under normal network conditions (TC01), communication between PC0 and PC1 was successfully established through three routers. In contrast, all four deliberately introduced fault scenarios (TC02–TC05) resulted in 100% packet loss during the recorded Ping tests.
The results indicate that missing or incorrect routing entries can disrupt network connectivity even when the physical connections remain operational.
In TC02 and TC03, removing a default route or a destination-specific static route prevented packets from reaching the intended network. In TC04, an incorrect next-hop address created a routing loop between Router0 and Router1, as demonstrated by the repeated addresses in the Traceroute output.
TC05 demonstrated the importance of return-path routing. Although packets could be forwarded toward the destination network, the missing default route on Router2 prevented successful communication with the source network.
These observations demonstrate that Ping failures alone are insufficient to determine the exact cause of a routing problem. Routing tables and Traceroute results provide additional evidence for locating and understanding connectivity failures. This is consistent with previous research on network diagnosis using routing information and end-to-end measurements [1], as well as Traceroute-based analysis of forwarding anomalies [3].
Interpretation of AI Diagnostic Results
The final Qwen3:4b assessments correctly identified the primary routing faults in all four faulty scenarios. However, the quality of the model's explanations and corrective recommendations varied.
In TC02, the model initially confused a missing default route with a missing destination-specific static route. After the actual baseline and faulty routing tables were provided with clearer analysis instructions, Qwen3 correctly identified the missing default route.
This result suggests that the model's diagnostic performance depends on the quality and completeness of the input information. However, because both the input data and instructions changed, the experiment cannot establish which factor was primarily responsible for the improvement.
In TC03 and TC05, Qwen3 correctly identified the missing routes but made inaccuracies when interpreting some Traceroute addresses. In TC04, the model successfully recognized the incorrect next-hop configuration and routing loop, although its recommended repair did not explicitly include removing the incorrect route.
These findings indicate that correctly identifying a network fault does not necessarily guarantee a complete or technically accurate troubleshooting explanation.
Interpretation of Fault Recovery
After restoring the original routing configurations, all four faulty scenarios returned to successful connectivity, with 0% packet loss in the recorded recovery tests.
This confirms that the identified configuration changes were sufficient to resolve the connectivity failures in the tested topology.
However, the corrections were applied manually in Cisco Packet Tracer. Therefore, the results demonstrate AI-assisted diagnosis rather than autonomous network repair.
The observed limitations also emphasize the importance of validating AI-generated configuration recommendations before implementation. Previous research on agentic network configuration repair similarly highlights the value of verification in improving the safety and effectiveness of AI-assisted repairs [9].
Overall Interpretation
Overall, the experiments suggest that Qwen3:4b can support the diagnosis of common static and default routing problems when provided with relevant network information.
Nevertheless, the results are limited to four fault scenarios within a single simulated topology. The observed diagnostic success should not be generalized to larger or more complex networks without additional testing.
The findings support the potential usefulness of AI-assisted network troubleshooting while highlighting the need for accurate input data, careful interpretation of diagnostic outputs, and manual verification of corrective actions.

This observation highlights the importance of validating AI-generated corrective actions before implementation.
Overall Comparison
Overall, previous studies demonstrate the effectiveness of network measurements, configuration analysis, machine learning, and formal verification in network troubleshooting [1], [2], [4], [6].
The present study provides a small-scale experimental evaluation of Qwen3:4b for diagnosing static and default routing faults using routing tables and Ping/Traceroute outputs.
Although the final assessments successfully identified the four introduced routing faults, the experiments also revealed limitations in explanation accuracy and corrective-action completeness.
Unlike studies conducted on large-scale or real-world network environments, the findings of this research are limited to one simulated topology and four routing fault scenarios. CHAPTER 5
DISCUSSION
5.1. Restate the Research Problem or Objectives
The primary objective of this capstone research was to design, evaluate, and critically analyze an AI-assisted diagnostic framework capable of detecting, localizing, and remediating static and default routing misconfigurations using exclusively operational CLI telemetry: routing tables (show ip route) and active diagnostic probe outputs (ping and traceroute). As conceptualized in Chapter 1 and substantiated in Chapter 2, manual network troubleshooting in multi-hop IP topologies is notoriously labor-intensive, error-prone, and severely inflates Mean Time to Repair (MTTR). Concurrently, traditional formal verification frameworks (such as Batfish [2] and Minesweeper [6]) demand exhaustive access to global configuration files, rendering them impractical for ad-hoc, localized incident triage.
To resolve these operational barriers, this study formulated three targeted research questions:
      1. RQ1: How can multi-modal control-plane routing state data be harmonized with dynamic data-plane diagnostic outputs to detect routing anomalies?
      2. RQ2: What is the efficacy of an intelligent reasoning model in localizing specific static and default route misconfigurations (missing routes, invalid next-hops, and default gateway omissions)?
      3. RQ3: How can the diagnostic reasoning and remediation recommendations generated by AI be made interpretable, technically complete, and verifiable to ensure operational trust for network engineers?
The empirical investigation executed in Chapter 4 evaluated these core objectives within an emulated multi-router Cisco network environment across five rigorous operational scenarios (TC01–TC05), utilizing a locally deployed Qwen3:4b large language model executing via Ollama. The subsequent sections synthesize the empirical findings, examine diagnostic anomalies and AI limitations, contrast results against the broader literature, and delineate practical boundary conditions.












5.2. Summarize Key Findings
The experimental outcomes obtained from the Cisco Packet Tracer testbed provide critical insights into the diagnostic capabilities and operational boundaries of the proposed AI-assisted troubleshooting framework across four key evaluation dimensions:
      1. Diagnostic Accuracy and Multi-Modal Telemetry Correlation (Addressing RQ1 and RQ2):
The empirical results compiled in Table 4.5 and Table 4.6 validate that correlating static control-plane routing tables with active ICMP data-plane telemetry provides an adequate, high-fidelity diagnostic signal to resolve static and default routing defects. In the baseline state (TC01), the combination of four-hop traceroute continuity and routing-table inspection established deterministic end-to-end reachability despite an initial transient 25% packet drop caused by Address Resolution Protocol (ARP) resolution latency. Conversely, each introduced single-point failure (TC02–TC05) produced catastrophic 100% ping packet loss, corroborating that static routing architectures completely lack autonomic self-healing capabilities [2], [6].
More crucially, the experimental observations substantiate the theoretical premise of RQ1: active probing alone is fundamentally insufficient to isolate root causes without control-plane correlation.
         * In TC04, traceroute captured an alternating hop sequence between 192.168.10.1 (Router0) and 10.0.12.2 (Router1), proving the existence of a forwarding loop and Time-to-Live (TTL) exhaustion. However, traceroute telemetry alone could not determine whether the fault originated from an erroneous static route on Router0 or a reciprocal misconfiguration on Router1. Only by cross-referencing Router1's routing table—which explicitly revealed "S 192.168.30.0/24 [1/0] via 10.0.12.1"—could the AI correctly diagnose that Router1 was forwarding packets back toward Router0 instead of downstream toward Router2.
         * In TC05, the data-plane symptoms demonstrated severe path asymmetry. Forward packets from PC0 traversed Router0 and Router1 before encountering silent timeouts at Router2, while reverse pings from PC1 were immediately rejected with "Destination host unreachable" by Router2 (192.168.30.1). Traditional black-box monitoring systems frequently misclassify such asymmetric unreachability as remote server downtime or firewall filtering. By correlating the forward and reverse traceroute outputs against Router2’s routing table ("Gateway of last resort is not set"), the system accurately deduced that packet transit failed exclusively on the return trajectory due to an absent default route.
Across all evaluated fault scenarios (TC02–TC05), the final diagnostic assessments achieved a 100% Fault Identification Rate (4/4) and correctly isolated the malfunctioning router (Table 4.7). This confirms that localized, text-based CLI outputs contain sufficient semantic density for AI models to diagnose common static routing failures without requiring global network telemetry graphs.
         2. Context Sensitivity, Incomplete Remediation, and Model Hallucinations (Addressing RQ3):
While the quantitative fault identification rate reached 100% in the final evaluation passes, a rigorous examination of the intermediate diagnostic steps and generated explanations reveals critical qualitative limitations inherent to generative AI troubleshooting (Table 4.8):
            * Prompt and Context Sensitivity (The TC02 Anomaly): In TC02 (missing default route on Router0), the initial zero-shot Qwen3 assessment misdiagnosed the failure mode. Rather than identifying that Router0 lacked a gateway of last resort, the model erroneously concluded that Router0 needed a specific static route to 192.168.30.0/24. While adding a destination-specific route would technically restore connectivity to PC1, it violates core architectural network design principles by failing to restore general egress reachability. Only after the operator supplied explicit comparative instructions juxtaposing baseline and faulty routing tables did the model correctly identify the missing "S* 0.0.0.0/0 [1/0] via 10.0.12.2" entry. This demonstrates that LLM diagnostic precision is highly sensitive to prompt structuring and contextual completeness.
            * Remediation Incompleteness (The TC04 Invalidation): A prominent finding of this research is the disparity between fault identification (100%) and complete corrective recommendation (75%, as shown in Table 4.7). In TC04, Qwen3 correctly identified the incorrect next-hop on Router1 and accurately explained the routing loop mechanics. However, its recommended CLI configuration script solely proposed adding ip route 192.168.30.0 255.255.255.0 10.0.23.2. Crucially, the model omitted the prerequisite removal command no ip route 192.168.30.0 255.255.255.0 10.0.12.1. In Cisco IOS, static routes to identical destination prefixes with identical Administrative Distances result in equal-cost multi-path (ECMP) load balancing rather than automatic replacement. Consequently, applying the AI's incomplete recommendation directly to production hardware would have resulted in 50% of outbound packets continuing to enter the destructive routing loop. This concrete observation underscores the acute danger of unvalidated AI remediation and provides empirical justification for incorporating formal configuration constraint checking before deployment [6], [9].
            * Semantic Interpretative Hallucinations: Despite recognizing correct root causes, Qwen3 exhibited persistent minor hallucinations in its natural-language narratives. In TC03, the model incorrectly asserted that the directly connected network 10.0.23.0/30 had disappeared from Router1, directly contradicting the provided show ip route output. In TC05, the explanation mislabeled router interface IP addresses (10.0.23.1 and 10.0.23.2) as endpoint host computers. Although human network engineers could easily filter out these narrative errors, they highlight that smaller quantized LLMs (4B parameters) can suffer from imperfect domain grounding. This reinforces the necessity of coupling LLM natural-language generation with deterministic symbolic verifiers under a strict human-in-the-loop paradigm.
            3. Synthesis and Contrast with Prior Art:
The experimental outcomes provide meaningful points of comparison against the established literature surveyed in Chapter 2:
               * Contrast with Active Probing and SAT Verification (NetDiagnoser [1] & Fontugne et al. [3]): Fontugne et al. [3] established that traceroute path anomalies indicate data-plane link disruptions, while Dhamdhere et al. [1] utilized Boolean tomography across multi-provider networks. Our findings confirm their assertion regarding the diagnostic value of hop sequences. However, while NetDiagnoser requires solving complex Boolean satisfiability equations across global network graphs, our localized AI-assisted paradigm isolates static routing faults within seconds using simple, single-device CLI snapshots.
               * Contrast with Formal Static Verification (Batfish [2] & Minesweeper [6]): Formal verification tools excel at mathematically proving reachability properties across complete enterprise configuration archives. However, as demonstrated in our testbed, generating complete configuration archives for quick troubleshooting of single-hop misconfigurations imposes severe administrative overhead. The Qwen3-based workflow successfully deduced routing loops and blackholes directly from transient CLI outputs. Nevertheless, the omission of the no ip route command in TC04 proves that LLMs lack the intrinsic correctness guarantees of SMT solvers, vindicating the architecture proposed in Objective 3 where LLM generative repairs must be constrained by formal verification rules [6], [9].
               * Contrast with Supervised ML and Agentic Repair (Mohammed et al. [4] & Asadli et al. [9]): Unlike the tabular classifiers trained by Mohammed et al. [4]—which output opaque classification labels (e.g., "Fault Class 2")—the LLM-based approach generated rich contextual explanations articulating why the packet failed and provided actionable Cisco IOS syntax. Furthermore, our findings align directly with the core conclusions of Asadli et al. [9]: while generative language agents hold immense potential for network configuration repair, unvalidated execution introduces substantial operational risk, establishing that human verification remains indispensable in production network administration.
               4. Threats to Validity and Methodological Boundaries:
To ensure scientific integrity, several methodological constraints of the experimental evaluation must be acknowledged:
                  * Topological Scale and Complexity: The empirical results are grounded in a controlled, three-router serial topology (PC0–Router0–Router1–Router2–PC1). While this architecture perfectly models edge-to-core demarcations, stub networks, and common CCNA/CCNP laboratory designs, it does not encompass arbitrary mesh networks, multi-homed BGP peerings, or high-density campus fabrics. The 100% fault identification rate observed in this small-scale testbed cannot be assumed to hold unconditionally in large-scale enterprise topologies without further empirical benchmarking.
                  * Diagnostic Modality Scope and ICMP Suppression: The system relies on the assumption that ICMP Echo and TTL Exceeded packets traverse intermediary hops unhindered. In enterprise networks where edge firewalls or Access Control Lists (ACLs) enforce strict ICMP rate-limiting or probe filtering (yielding * * * responses in traceroute), data-plane path visibility becomes obscured. In such scenarios, the diagnostic engine must rely more heavily on cross-correlating adjacent control-plane routing tables.
                  * Absence of Dynamic Protocol Interactions: The investigation strictly evaluated static routes and default routes (0.0.0.0/0). In production environments, static routes frequently interact with dynamic interior gateway protocols (such as OSPF, EIGRP, or BGP) through route redistribution and floating static metrics. Extending this troubleshooting framework to dynamic protocols will require tracking route convergence timers, link-state advertisement (LSA) flooding, and dynamic metric recalculations.
                  * Manual Pipeline Execution: In the reported experiments, CLI outputs and connectivity logs were extracted and fed into the Ollama Qwen3 model via manual prompt engineering, and corrective commands were executed manually by human operators. While this methodology rigorously validated the diagnostic reasoning capabilities of the model, fully realized practical deployment demands an automated ingestion daemon utilizing TextFSM parsers and an interactive user interface.
